Context

Why this exists

The dashboard went through three passes — the V2 “Aurora Glass” pilot, a V3 composition and brand pass, and a light-mode settle — and came out genuinely enterprise-grade: an ambient canvas, a three-tier glass material system, a brand-derived token layer, real metric tooltips, measured 60fps scroll.

The rest of the app never moved. Today a user crossing from /dashboard to /mrf watches the chrome stay glass while the content drops to flat cards — which is worse than either extreme. The old phase list was also written to a narrower brief (“widen a boolean, fix what breaks”), and it has since drifted from the code: it schedules a page that no longer exists, and it defers the single largest visual gap in the app indefinitely.

The brief

Never trade design quality for rollout speed. Where the old plan deferred something awkward, this one schedules it. Every surface a user can reach — page, dialog, control, empty state, public token page — reads as one deliberately designed product, in both themes, with no half-converted screens at any point in the sequence.

Four corrections

What the old plan got wrong

Each of these was found by surveying the code, not by reading the previous plan.

1

40 dialogs were deferred indefinitely

37 <Modal> and 3 <Drawer> across the app — PipelineDrawer.jsx alone holds 10 modals and a drawer. They portal into document.body, structurally outside .ats-v2, so the old plan’s answer was “leave AntD’s default chrome untouched app-wide… open question.” On a glass app that means every dialog opens as a flat white box. It is now Phase 1.

2

AnalyticsLegacy.jsx does not exist

The old Phase 3 targets /analytics-legacy. There is no such route and no such file — only /analytics is live. A phase was scheduled against a deleted page.

3

.glass-3 has zero consumers

The tier-3 class has never been used by any page — the Recent Candidates table it was written for was replaced by LatestUploads. Its .ant-table rules are unverified against a real table. The first phase that uses it must verify them.

4

Every .glass-card is silently blurring

aurora-glass.css:256 documents “NO backdrop-filter on scrolling content surfaces,” but the base rule at index.css:850 sets backdrop-filter: blur(12px) and the .ats-v2 override never cancels it. The documented design and the shipped code disagree today.

Also corrected

package.json pins antd ^5.17.0, but 5.29.3 is installed. This matters: the overlay tier depends on ConfigProvider’s modal / drawer config, verified present in the installed config-provider/context.d.ts. Bump the pin before Phase 1, or a clean npm install on another machine breaks it.

Part I · The design system

Material tiers

The core idea: a surface’s translucency is a function of its information density, not its importance. A hero and a hundred-row table want opposite things from glass.

1 Chrome Sidebar, topbar — sticky, rasterized once, never scrolls blur
2 Feature Hero, KPI cards, widget and panel cards, board columns no blur
3 Data Tables, dense lists, any row nested inside a tier-2 card no blur
4 Overlay Modals, drawers, popovers, dropdowns — new in Phase 1 blur

Rules that follow, and are not negotiable per page

  • A surface nested inside a tier-2 card is tier 3. Already established by .dash-uploads__row and .quick-action-row on the dashboard, and by .cand-card in the last phase.
  • Only tiers 1 and 4 blur. Tiers 2 and 3 scroll, and a backdrop-filter on a scrolling surface re-blurs its backdrop every frame — over soft gradients with 3% grain it buys nothing visible. This is measured, not assumed.
  • Light-mode chrome is opaque white, not tinted glass. A translucent pane is only ever as neutral as what shows through it; lowering alpha cannot achieve this. Already shipped — do not “fix” it back.

The inline-style law

This rule determines the effort of every phase, so read it once carefully. An inline style={{ background: … }} cannot be overridden by any stylesheet without !important — and !important in a stylesheet beats a non-important inline declaration. That asymmetry produces two distinct failure modes, and you need to recognise both.

Failure A

The slab

A page card carries .glass-card, but a panel inside it paints an inline --ink-3 fill. The card goes translucent; the panel stays a flat rectangle stuck to the glass. The last phase hit this on every nested surface of both its pages.

on a translucent pane
Failure B

The silent kill

A rule using the border shorthand with !important overrides an inline borderInlineStart that was carrying data — a status colour. The information disappears with no error. Phase 4 will hit this on .cp-candidate-card.

status accent erased
by a shorthand border

The remedy, in the order you should reach for it

  1. Move the declaration into a class whose values are byte-identical to what they replace, so nothing outside .ats-v2 shifts by a pixel. Only then can the scoped rule restyle it.
  2. If the value is data-derived — a status colour, a metric hue, an avatar colour — pass it as a CSS custom property and let CSS own the property. Established twice already: --stat-color on StatCard, --kpi-color on KpiCard. This is the fix for Failure B.
  3. Never use the border shorthand on a surface whose border encodes meaning. Set border-block and border-inline-end, and leave the meaningful side alone.

The overlay tier

Forty dialogs cannot be converted by hand without drift, and they are unreachable from .ats-v2. Both problems have one solution — component-level config on the existing provider, verified against the installed antd 5.29.3:

<ConfigProvider
  theme={currentTheme}
  modal={{ classNames: { content: 'ats-overlay', mask: 'ats-overlay-mask' } }}
  drawer={{ classNames: { content: 'ats-overlay', mask: 'ats-overlay-mask' } }}
>

Every dialog in the app then carries the class wherever it portals to — no per-file JSX edits, no getContainer changes. One CSS block, written unscoped on purpose, because portals sit outside .ats-v2 by construction. The same mechanism extends to Select, Dropdown, Tooltip, Popover and DatePicker panels, all of which portal to body and are flat today.

Respect what exists

Three dialogs have bespoke treatments that must survive: .conv-modal, .dash-cmdk, and the global .ant-modal viewport caps at index.css:1741 — those caps are a real fix for footer buttons becoming unreachable on small laptops. Do not regress them.

Primitives to build once, then reuse

The dashboard invented these; the rest of the app re-implements them ad hoc. Building them in Phase 2 is what stops phases 3–8 from drifting.

PrimitiveStatusAction
MetricInfo + registryBuilt, dashboard-onlyExtend as phases surface new metrics. Analytics and Vendor KPIs have none today.
StatCardBuiltAdopt on /analytics in place of ad-hoc tiles — gains tooltips it lacks.
KpiCardGlass rules inertActivates Phase 5 with zero JSX change.
Empty statesAd hocOne component. Explain why it’s empty, offer the next action. A bare “No data” is not acceptable.
Loading statesMixed spinner / skeletonSkeletons shaped like what’s loading, not a centred spinner that collapses layout.
Error statesAd hoc AlertOne component; actionable message plus retry.
Density scaleUndefinedDefine once. Control heights and row padding vary per page for no reason.

Motion. Every animation is transform / opacity only. Never animate background-position. Never use mix-blend-mode on a full-viewport layer — measured at 23% of frames over 20ms, versus ~3% without. The app-wide prefers-reduced-motion guard zeroes all of it for free.

Accessibility applies to every phase, not a final pass. Each phase adds its own new surfaces to the existing prefers-reduced-transparency block. Carve-outs are allowed only where translucency carries the only cue for state. Contrast holds in both themes — the dark-mode sweep fixed ~200 hardcoded colours, and every phase re-checks its own screens before calling done.

Part II · Execution

Nine phases

System before surfaces, then routes in ascending order of structural risk. Phase 1 removes the biggest visual gap and unblocks everything after it; Phase 2 builds the primitives so phases 3–8 apply rules rather than invent them. The numbering is a real dependency order, not a label.

The gate is V2_ROUTES at MainLayout.jsx:108. Advance the rollout by adding to that array; revert any phase by removing its entry.

Decision

Public pages and auth

Currently outside the glass system by construction — and partly that is correct.

  • Public token pages render outside MainLayout under ForceLight. PublicPageShell deliberately mirrors the branded email shell so the click-through feels continuous — that is a correct decision and glass would break it. Recommendation: keep the shell, bring typography, spacing, density and the Phase 2 primitives into line. These are the only AAPNA surface most external people ever see.
  • AuthLayout is a distinct tree, and /login is the pilot’s own pixel-diff non-regression anchor. Changing it means re-baselining that anchor — do it knowingly or not at all.
Verification

Definition of done

Every phase, no exceptions. The per-phase checks guarantee no single phase regressed; the final walk is the actual acceptance test.

  1. npm run build clean.
  2. Verified in both themes.
  3. New surfaces added to the prefers-reduced-transparency block.
  4. Inline-style audit of every file touched — no Failure A slabs, no Failure B silent kills.
  5. Raw brand hexes in touched files replaced with tokens.
  6. Shared-class non-regression — assert on computed styles, not screenshots alone.
  7. Scroll-perf probe for any table, list or board: continuous rAF, one scrollBy per frame. A wheel-then-wait probe reports phantom drops here — a documented trap.
  8. UI-CHANGELOG.md entry: what was built, what was deliberately left, what was verified.
Run the perf probe on an idle machine

A previous session returned ~99% dropped frames on every arm including the no-glass control. That was a throttled host — the disk had hit zero bytes free — and it measures nothing. Uniform results across all arms means the host, not the design.

Final acceptance, after Phase 8: walk every sidebar route in both themes, in one sitting, opening at least one dialog per screen. No screen may read as belonging to a different product than the one before it.

Explicitly out of scope

No phase touches data fetching, aggregation, permissions, pagination, scoring, the shortlist and reject flow, or email sending. Every phase here is visual. Pipeline.jsx in particular persists real data and sends real candidate emails — visual-only changes there, no exceptions.

Open items

Decisions for the team

Phase 8 — convert the prototype, or retire it?

It is a demo page, off the sidebar, kept for client walkthroughs and cited as a design reference by several components. Converting costs a phase; leaving it makes it look abandoned beside the real board.

Phase 9 — how far into the public pages?

Recommendation above is typography, spacing and primitives only, keeping the email-mirroring shell intact.

Bump the antd pin before Phase 1

package.json says ^5.17.0; 5.29.3 is installed. The overlay tier needs ≥5.19 for the provider config. A clean install elsewhere breaks it otherwise.
